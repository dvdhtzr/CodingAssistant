# Owner data and evidence retention (#72)

## Default retention and boundaries

CodingAssistant is single-owner and local-first. The control-plane database retains project objectives, specification/interview content, approved plans, model names, saved generated source, and independent QA/repair findings until the owner explicitly deletes that project. There is no automatic expiry or silent pruning of approvals or evidence. Live HTTP activity is a bounded 120-entry in-memory ring (40 per response) cleared at process restart. It contains route templates, method, status, time and latency only. Raw URLs, query strings, bearer credentials, request/response bodies, raw inference streams, and raw tool logs are not activity records. Hosting request diagnostics that could contain raw URL queries are disabled. Other operational errors remain bounded by the existing sanitization contracts.

M1 private execution ledger stores identifiers, states, immutable plan hashes, fixed evidence names and evidence hashes, not prompts, credentials or raw inference logs. Host-owned independent receipts are local and Git-ignored. An incomplete or recovery-blocked ledger must not be deleted to bypass a safety gate. Owner-authenticated project deletion refuses active execution or unresolved recovery and removes the selected project's durable control-plane rows transactionally. SQLite secure_delete is enabled on application connections; this does not guarantee forensic erasure from WAL, backups, filesystems, SSDs or OS snapshots. Previously exported ZIPs and M1 private receipts are separate; do not remove them until reconciled and no longer needed. The application does not automatically delete host exports or backup copies.

## Storage

Use the normal per-user local application data folder or an explicitly selected private local folder. Do not place it in a repository, synced/shared directory, cloud share or network-mounted filesystem. Unix requires 0700 for the data directory and owner-only read/write for DB/sidecars; Windows ACLs permit only the current user, SYSTEM and local Administrators (creator-owner inheritance is permitted). A new Windows directory is created with protected owner ACLs. An existing unsafe directory is rejected without silently changing ACLs. Existing database and sidecar links are refused. These checks are not a sandbox against a malicious same-account process or a privileged OS administrator; do not run the service with untrusted code under the same account. Windows owner credentials use DPAPI CurrentUser; never include the token in logs, URLs or SQLite. Do not store API keys or other secrets in task objectives, specs, code or model inputs. Inputs intentionally retained for authoring are not automatically redacted from the private project itself.

## Offline backup and restore (owner action)

1. Stop the local UI/API and all workers. Reconcile every uncertain container before backup; do not use a restore to bypass execution recovery. Confirm no processes have the database open. Use OS access controls and encrypted private storage for the backup.
2. Copy the complete private database directory (including any SQLite WAL/SHM or rollback journal present) to an owner-only backup. Do not copy a live WAL database with a file-by-file process. Keep private M1 evidence/ledger and receipts separate, preserving exact names and hashes. The DPAPI credential only decrypts under the same Windows account; do not share it. Never commit or upload backups as part of development.
3. To restore, stop everything again; preserve the existing directory as a separate private rollback copy; restore the complete matching snapshot, with owner-only permissions. Never restore a stale ledger while a real guest is active. Start in normal non-executable mode, verify project history and source, and review recovery state before any new approval. Treat restored approvals as historical, not new authorization.
4. To remove data, use the authenticated project delete action after safe reconciliation, then independently remove owner-chosen exports/backups no longer needed. Backups may retain deleted content; dispose of them according to your own retention needs. For SQLite forensic erasure use appropriate whole-volume encryption/OS disposal, not a claim that the UI delete wipes storage.

The Git ignore contract covers misplaced standard control-plane DB, ledger and credential names and ignored artifact roots; it does not prevent deliberate forced adds or arbitrary renamed exports. Review staged files before commit. No new network endpoints, telemetry, cloud model, permissions or automatic data deletion are introduced.
